# ADR 0001 — Persistence, streaming, and distribution without bloating the default build

- **Status**: Accepted
- **Date**: 2026-06-10
- **Release**: 1.2.0

## Context

The 1.2 roadmap added five capabilities to szal: condition caching, flow
versioning/migration, persistent execution stores (SQLite + PostgreSQL),
distributed DAG execution, and step output streaming over SSE/WebSocket.

szal is a flat library crate consumed by daimon, AgnosAI, and sutra. Its guiding
constraints (see `CLAUDE.md`) are *keep it lean — no unnecessary dependencies*
and *own the stack*. Three of the five features (caching, versioning) are pure
and add nothing. The other three pull in real weight: a SQL driver stack, and a
transport for streaming. Adding those unconditionally would tax every consumer,
including those that want none of it.

## Decision

**Feature-gate everything heavy; keep the default build dependency-free.**

1. **Execution stores** live behind `sqlite` / `postgres` Cargo features, each
   enabling `sqlx` with only the matching driver (no TLS feature by default).
   The default build pulls no database crates. A single `szal_executions` table
   stores each `ExecutionRecord` as JSON, so the SQL is identical across backends
   except for bind-parameter placeholders — generated once via a macro.

2. **The engine stays synchronous.** The existing `ExecutionStore` trait (sync)
   is unchanged, preserving the engine's API and existing consumer impls. sqlx is
   async, so `engine_sink()` bridges the two: writes go through a **single ordered
   background writer task** (guaranteeing a flow's `Running` save cannot overwrite
   its later `Completed` save) and an in-memory mirror serves the sync reads.
   Consumers wanting DB-authoritative queries use the async API directly.

3. **Streaming ships encoding, not a server.** `stream::ProgressHub` is a thin
   `tokio::sync::broadcast` hub; `progress_to_sse()` emits `text/event-stream`
   frames. The transport (axum, tungstenite, …) stays in the consumer. No
   web-server dependency enters the library.

4. **Distributed DAG reuses majra.** `Engine::run_distributed` (the `fleet`
   feature) coordinates a DAG over `majra::fleet::FleetQueue` rather than adding a
   new distribution primitive — *own the stack* via the AGNOS crate that already
   wraps it.

## Consequences

- The default `cargo build` is unchanged in dependency weight; `--all-features`
  pulls sqlx (and its tree, which added the `Zlib` license to `deny.toml`).
- `engine_sink` persistence is eventually-consistent and ordered, not
  synchronous-durable; documented on the type. Crash recovery (replaying
  persisted records) is deferred to 1.3.
- Distributed execution models independent engine instances as fleet nodes —
  in-process today; cross-host requires backing the fleet queue with a
  distributed transport (1.3).
- Two backends share one macro-generated implementation, so a third SQL backend
  is a small addition.
